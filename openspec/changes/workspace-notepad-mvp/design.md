# Design

## Context

Проект с нуля (пустой репозиторий). Приоритет пользователя: **максимальная скорость**, нативное десктоп-приложение на **Rust** с кроссплатформенным GUI. Платформы: macOS (рабочая машина) и Windows; Linux — желательно. Требования — в `specs/` этого change.

Исследование Rust GUI-стеков (октябрь 2026, 5 итераций: areweguiyet.com, обзор boringcactus 2025, блог Zed, lap.dev, данные crates.io) — в разделе D1.

## Goals / Non-Goals

**Goals:**
- Мгновенный запуск, 120 FPS GPU-рендеринг, отзывчивость на файлах в десятки МБ (уровень Zed/Notepad++).
- Одна кодовая база Rust для macOS/Windows/Linux.
- Богатый редактор: multi-cursor, folding, закладки, regex.

**Non-Goals:**
- Интеллектуальное автодополнение/LSP-фичи как в IDE.
- Плагины и макросы (вне этого change).
- Web-версия приложения.

## Decisions

### D1. GUI-фреймворк: исследование и выбор

Анализ (актуальность: окт 2026):

| Фреймворк | Скорость/рендеринг | Зрелость (crates.io) | Готовый editor-widget | Кроссплатформенность | Вердикт |
|---|---|---|---|---|---|
| **GPUI** (Zed) | GPU, hybrid imm/retained, 120 FPS, доказан Zed на файлах гигабайтов | v0.2.2, 179k скач./90д, docs-сайт, сторонние продукты (Delta) | Нет, но Zed доказал модель; editor-паттерны открыты | macOS + Windows (с окт 2025) + Linux | **Кандидат №1** |
| **Floem** (Lapce) | GPU (wgpu) + CPU fallback, «bare metal» | v0.2.0 на crates.io с ноя 2024, развивается в репо Lapce | Нет (Lapce строит свой) | Win/mac/Linux | Кандидат №2, но экосистема малая, IME/a11y нет (2025) |
| **egui** | Immediate mode, GPU | v0.36.2, огромная экосистема (25M скач.) | `egui_code_editor` — только базовый | Win/mac/Linux/web | Надёжный fallback; для «максимальной скорости» и тяжёлого редактора слабее |
| **iced** | wgpu | v0.14, активен (System76/COSMIC) | Нет | Win/mac/Linux | Text editing примитивен, IME нет |
| **Slint** | GPU | v1.18, активен | Нет (LineEdit) | Win/mac/Linux/embedded | Отличные a11y/IME, но не для код-редактора; DSL |
| Dioxus/Tauri | webview | — | CodeMirror/Monaco | — | Отклонено: не нативная скорость (требование пользователя) |

**Решение: GPUI.**
- Единственный фреймворк, на котором уже построен production-редактор мирового класса (Zed 1.0, апр 2026; Windows с окт 2025) — доказана и скорость, и возможность реализовать все наши specs.
- GPUI теперь standalone: крейт на crates.io, сайт gpui.rs с примерами и документацией.
- GPU-ускоренный hybrid immediate/retained рендеринг — лучший профиль для мгновенного UI.
- Минусы принимаем осознанно: API привязан к ритму Zed (churn), документация скуднее egui, готового editor-виджета нет — движок редактора пишем сами (см. D2).

**Fallback-план:** если spike (см. Risks) покажет, что GPUI нестабилен для стороннего приложения — переход на egui (наибольшая экосистема, предсказуемость) с отдачей части производительности.

### D2. Движок редактора (своя разработка на GPUI)

Никакой Rust GUI-фреймворк не даёт готовый код-редактор — строим свой по модели Zed:
- **Текстовая модель**: rope-структура `ropey` (12M скач., betav2) — O(log n) вставки/удаления, мгновенный доступ к строкам; сумма-дерево для метаданных строк (закладки, folding-диапазоны, подсветка).
- **Multi-cursor / column selection**: множество `Selection` (диапазон + реверс-флаг) поверх rope; ввод/удаление транзакциями на все курсоры.
- **Folding**: диапазоны от дерева синтаксиса, свернутые строки скрыты в layout.
- **Поиск/замена**: regex-движок `regex` + `fancy-regex` (lookaround) по rope с мемоизацией.
- **Подсветка**: `syntect` (Sublime-синтаксисы, 100+ языков, потоковый парсер — быстрая интеграция 70+ языков сразу) как MVP-уровень; tree-sitter — опционально позже для точности. Уровень детализации: инкрементальная раскраска только видимой области.
- **Рендеринг**: GPUI text elements, отрисовка только видимых строк (virtualized) — критично для 10 МБ+.

### D3. Поиск по файлам в папке
Rust: параллельный обход дерева (rayon) + memmap-сканирование без загрузки файлов в память; кодировки через `encoding_rs` + `chardetng`; потоковая выдача результатов в UI.

### D4. Watch файловой системы
`notify` (FSEvents / ReadDirectoryChangesW / inotify) + дебаунс; полный рескан как fallback.
### D5. Состояние сессии

JSON в каталоге данных приложения: воркспейс, вкладки, активная вкладка, настройки (тема, шрифт). Без БД. Детали реализации группы 3 — D8.4.

### D6. Кодировки и переводы строк
BOM → валидация UTF-8 → эвристика chardetng; конвертация `encoding_rs`. Переводы строк: нормализация в модели при загрузке, обратная конвертация при сохранении (подход VS Code).

### D7. Локализация
Все строки UI — через ключи; переводы во внешних файлах (формат: JSON или TOML, один файл на язык, `locales/en.toml` — источник). Загрузка при старте, fallback на английский для отсутствующих ключей. Реализация: крейт `rust-i18n` или простая своя обёртка (Map<String, Map<String, String>>) — выбор на этапе реализации, поведение по specs.

### Spike Results (задачи 1.3–1.4, окт 2026)

**D2.1 Реализация транзакций (задача 2.1, окт 2026).** `Edit` = замена диапазона char-индексов текстом; `Transaction` = батч правок, отсортированных по возрастанию, позиции — в координатах документа **до** транзакции. Применение — в обратном порядке (большие позиции не сдвигают меньшие), инверсия вычисляется за один проход с кумулятивным сдвигом: `inverse[i] = { start: s_i + Δ_i, end: +len(insert_i), text: removed_i }`. Инверсия структурно симметрична (`inverse.apply == original`) — база undo/redo (2.4). Пересекающиеся правки отбрасываются при построении, касание по границе (`start == last.end`) допустимо. `map_position(pos, bias)` — для маппинга выделений (2.2).

**D2.2 Selection и multi-cursor транзакции (задача 2.2, окт 2026).** `Selection { start, end, reversed }` — char-индексы, `start <= end`; каретка = вырожденное выделение; `Selection::range(a, b)` нормализует порядок, `reversed` означает, что голова слева от якоря (`head()` — меньший индекс). Транзакции над всеми курсорами — свободные функции в `selection.rs`: `insert_text(&[Selection], text)`, `backspace(len_chars, &[Selection])`, `forward_delete(len_chars, &[Selection])` → `Transaction` (пересечения отбрасывает `from_edits`); backspace удаляет ровно один char перед кареткой (документ LF-нормализован по D6), каретка в позиции 0 / forward delete в конце — no-op. `Transaction::map_selection`: каретка — `Bias::Right` (смещается за вставленный текст), диапазон — начало `Bias::Left`, конец `Bias::Right` (растягивается вокруг вставки; при полном удалении диапазон схлопывается в каретку); `reversed` сохраняется. Следствие политики Left/Right: ввод поверх выделения оставляет выделение поверх введённого текста — схлопывание в каретку после ввода делает editor-виджет (группа 4) поверх map_selection.

**D2.3 Метаданные строк (задача 2.3, окт 2026).** `LineMeta` (crates/editor-core/src/line_meta.rs) — order-statistic treap над строками: арена из `Vec<Node>` (u32-индексы, без внешних зависимостей), max-heap по случайному приоритету (детерминированный splitmix64 — воспроизводимые тесты). В узле: флаги `bookmark`/`folded` и суммы по поддеревьям (size, bookmark_count, fold_count) → вставка/удаление диапазона строк, точечная установка флага и запрос агрегатов — O(log n); `bookmarked_lines()`/`folded_lines()` — O(n) обход (нужны целиком для панели закладок и рендера). Char↔line не дублируется — ropey даёт O(log n) `char_to_line`/`line_to_char`; treap хранит только метаданные. Номера строк 0-based.

**D2.4 Undo/Redo через транзакции (задача 2.4, окт 2026).** `History` (crates/editor-core/src/undo.rs) — два стека **групп**: группа = упорядоченный вектор транзакций-инверсий одного «сеанса ввода»; каждая запись валидна в координатах состояния сразу после своей правки (такую инверсию возвращает `Document::apply`). `undo` применяет записи группы от новой к старой — каждый шаг возвращает прямую транзакцию, из которых собирается группа redo-стека; `redo` симметричен. Каждый шаг — корректная пара apply/inverse (инвариант `inverse.apply == original`), координаты не пересчитываются вовсе; LineMeta синхронизируется автоматически внутри `Document::apply` — закладки/folded переживают undo/redo. Группировка — только «подряд по типу»: транзакции, все правки которых — одиночные вставки символов (кареток может быть несколько) либо одиночные удаления, образуют одну группу, пока идут подряд; таймауты и позиционные эвристики сознательно не используются. **Слияние групп в одну транзакцию пересчётом координат отвергнуто**: для групп с немонотонным движением каретки (последовательный forward-delete; ввод после возврата каретки внутрь уже введённого) порядок вставок в одной позиции неоднозначен при любом выборе `Bias` (реальный падающий тест: 3× forward-delete → один undo давал «cbadef» вместо «abcdef»); группировка вектором транзакций свободна от этого класса ошибок. Следствие: `Transaction::edits_mut` не понадобился и удалён. Правка другого типа, составная правка (замена, многосимвольная вставка/удаление) и undo/redo закрывают группу; новая правка очищает redo-стек; пустые транзакции (no-op) не регистрируются. API: `History::apply(doc, tx)`, `push(tx, inverse)` после ручного применения, `undo/redo(&mut Document) -> bool`, `can_undo/can_redo`.

**D2.5 Кодировки и переводы строк (задача 2.5, окт 2026).** `crates/editor-core/src/encoding.rs` + `Document::load_file_detected/save_file/format/encoding/line_endings` (для статус-бара 3.5). Загрузка — один потоковый проход в общем случае: префикс 64 КБ → BOM (UTF-8/UTF-16LE/BE — декодирование фиксированное) → иначе потоковая валидация UTF-8 (`Decoder::decode_to_string_without_replacement`) с построением rope на лету (`RopeBuilder`) и параллельным кормлением chardetng; при первом malformed байте — `guess(allow_utf8=false)` и перечитывание файла с начала в предположенной кодировке. Всё читается кусками по 64 КБ, файл целиком в память не попадает (в памяти только префикс). Декодирование lossy (U+FFFD) для BOM- и chardetng-путей — файл невозможно «не открыть»; файлы без BOM, прошедшие UTF-8-валидацию, декодируются без потерь. Переводы строк: нормализация CRLF/CR → LF при загрузке (D6; перенос `\r|\n` через границу кусков — конечным автоматом с pending-CR), статистика LF/CRLF/CR — по исходному тексту; при сохранении — обратная конвертация в доминирующий формат (большинство; при равенстве LF > CRLF > CR; без переводов — LF). Round-trip байт-в-байты гарантирован для файлов с единообразными переводами строк (обязательный тест — матрица кодировки × формат); смешанные файлы нормализуются в доминирующий формат; BOM сохраняется. Новые документы — UTF-8 без BOM, LF (платформенно-независимый дефолт: кроссплатформенная предсказуемость важнее локального дефолта ОС; смена формата — будущая настройка). Сохранение потоковое: `Rope::chunks()` → конвертация переводов → кодирование; **UTF-16 кодируется своей конвертацией** (`str::encode_utf16`), т.к. в encoding_rs UTF-16 — не output encoding (`new_encoder()` для него вернул бы UTF-8-энкодер); декодирование UTF-16 — штатным Decoder. `Document` хранит `FileFormat { encoding, line_endings }`; `Document::load_file` (UTF-8 без детекта) сохранён — используется spike-тестами.

Привязка к документу: индекс — поле `Document`, синхронизируется автоматически в `Document::apply` **до** мутации rope (доступ через `line_meta()`/`line_meta_mut()`); отдельная ручная синхронизация не нужна, рассинхрон невозможен. Для каждой `Edit` в до-транзакционных координатах: `line = char_to_line(edit.start)`, число удаляемых строк = количество `'\n'` в удаляемом тексте, вставляемых = в `edit.text`; правки обрабатываются по возрастанию с кумулятивным дельта-сдвигом строк. Привязка флагов — к содержимому строки: если `edit.start` на границе строки (вставка/удаление целых строк), диапазон строк начинается с самой строки `line` (при вставке старая строка с флагами уезжает вниз за содержимым); если `edit.start` внутри строки — строка `line` сохраняет флаги, диапазон начинается с `line+1`. Итог: закладки переживают вставку строк выше (обязательный тест), флаги целиком удалённых строк исчезают, нетронутые строки сохраняют флаги. Освобождённые узлы treap не переиспользуются (арена растёт монотонно) — для MVP достаточно, компакция при необходимости позже.

Spike-редактор в `crates/app` (main.rs): ropey 1.6 (streaming `Rope::from_reader`) + GPUI 0.2.2 `uniform_list` (рендер только видимых строк), ввод/удаление — мутации rope по char-индексу. Файл теста: 5 000 052 байт, 53 765 строк (`/tmp/notepad-spike-5mb.txt`).| Метрика | Результат | Критерий | Вердикт |
|---|---|---|---|
| Открытие файла 5 МБ (debug-сборка) | 174–194 мс | < 1 с | **pass** |
| Rope-мутация на нажатие | ~0.02 мс | — | отлично |
| Нажатие → отрисовка (81 нажатие, event→render) | max 14.8 мс (типично 4–14 мс) | < 16 мс | **pass** |
| Первый keystroke после фокуса | 148.7 мс (разовый прогрев первого кадра) | — | не влияет на интерактив |

Наблюдения: латентность ввода на файле 5 МБ стабильно ниже 16 мс (порог 60 FPS); rope-мутации пренебрежимы, стоимость почти целиком в layout/render видимых строк — подтверждает подход virtualized-рендера (D2). Видимая каретка не рендерилась (только подсветка текущей строки) — осознанно, вне scope spike.

**Вердикт: spike пройден. GPUI подтверждён, fallback на egui не требуется.**

### D8. Каркас приложения — группа 3 (окт 2026)

Нумерация D8 (не D3, как изначально предполагалось): D3–D7 в этом документе заняты; подразделы D8.1–D8.5 соответствуют задачам 3.1–3.5. Структура кода: `crates/app/src/{main.rs, workspace.rs, tab_model.rs, session.rs, language.rs}`.

**D8.1 Layout и минимальный редактор (3.1).** Один корневой view `Workspace`: панель «Project» слева 220px (заглушка до группы 7), центр — таб-бар + редактор, статус-бар внизу. Редактор минимальный, spike-образный: `uniform_list` (virtualized — файл 5 МБ открывается/скроллится без лагов), Menlo 13px, высота строки 20, гуттер с номерами. Весь editing-клей (Document::apply + History + маппинг каретки через `map_selection`) — в GPUI-free `BufferTab` (tab_model.rs), GUI только форвардит клавиши; `TabModel` покрыт интеграционными unit-тестами без GUI, view — 6 тестами на `gpui::test` (`simulate_keystrokes`/`dispatch_action`: ввод, стрелки, backspace/enter, Cmd+S на диск, Undo/Redo, CloseTab). Каретка одна, рендер — строка каретки разрезается в позиции каретки, между половинами 2px-див (точная позиция без метрик шрифта) + подсветка строки. Действия (`on_action`) висят на корневом div — работают и при пустом списке вкладок; plain-клавиши — `on_key_down` редактора. Клавиши: Cmd+O/S/Shift+S/W/Q **+ Cmd+Z/Shift+Z** — undo/redo добавлены к минимальному набору, т.к. History — неотъемлемая часть editing-пути (полный справочник — 8.5). Навигация: стрелки/Home/End; клик-позиционирование, PgUp/PgDn, выделения — 4.2. Заголовок окна = активная вкладка (кэш, `set_window_title` только при изменении).

**D8.2 Вкладки (3.2).** `TabModel` (GPUI-free): `Vec<BufferTab>` + активный индекс + untitled-счётчик; вкладка = `{ path: Option<PathBuf>, doc, history, cursor: Selection, dirty, scroll_y }`. Dirty ведётся в модели (правка → true, успешный save → false), editor-core не расширен; undo/redo НЕ сбрасывает dirty (нет baseline «сохранённого состояния» — принято). Перестановка — кнопки ◂ ▸ в таб-баре (двигают активную вкладку); drag-and-drop отвергнут для MVP: в gpui 0.2.2 drag требует ghost-Render view — вернуться позже. Повторное открытие того же пути активирует существующую вкладку (дедупликация без каноникализации — диалоги ОС дают нормализованные пути). Закрытие dirty-вкладки — модальный `Window::prompt` (Save / Don't Save / Cancel; Save на untitled сначала save-as, отмена диалога оставляет вкладку); закрытие активной активирует правую соседку, крайней — левую. Untitled: `Document::new()` (UTF-8/LF по D2.5), заголовок «Untitled N» по порядку среди untitled (перенумерация при закрытии).

**D8.3 Открытие файла (3.3).** Диалоги ОС — штатные в gpui 0.2.2: `App::prompt_for_paths` (открытие, мультивыбор) и `App::prompt_for_new_path` (save-as). **rfd не добавлен** — нативных диалогов достаточно, зависимостей меньше. Вкладка для файла вне воркспейса неотличима от обычной. Файловый IO (`load_file_detected`/`save_file`) синхронный на main thread: spike-замер ~180 мс на 5 МБ в debug приемлем; фоновая загрузка — при необходимости позже.

**D8.4 Сессия (3.4).** Путь: crate `dirs` (v6) → `data_dir()/notepad-plus/session.json` (macOS: `~/Library/Application Support/notepad-plus`); ручная сборка пути отвергнута — лишний код. Поля: workspace (None до группы 7), tabs (только с путями), active_tab (пересчитанный индекс среди сохранённых), window {x,y,w,h}. **Untitled-вкладки не сохраняются** (контент больше нигде не живёт), **dirty не сохраняется** — восстановление перечитывает файлы с диска, несохранённые правки при выходе теряются (стандартное поведение). Восстановление — чистая функция `session::plan_restore` (unit-тесты: пропуск несуществующих, пересчёт активной — пропущена → ближайшая предыдущая выжившая): несуществующие файлы пропускаются, сообщение в статус-бар («Skipped N tab(s)…»), без таймера — живёт до следующего сообщения. Геометрия: валидация (w,h ≥ 200, конечные значения), иначе окно по центру; off-screen позиция не проверяется (macOS обычно кадрирует сам); сохраняется внешняя граница окна (728 = 700 контента + 28px заголовок) — позиция/размер восстановились точно (проверено Quartz-замером и вручную). Триггеры сохранения: `on_app_quit` (Cmd+Q/платформенный выход; подписка `.detach()` — живёт всё приложение) и `on_window_should_close` (красная кнопка: сессия сохраняется, окно закрывается, приложение живёт; клик по док-иконке `on_reopen` открывает окно заново с восстановлением). SIGTERM сессию не сохраняет — принято. Scroll-позиция вкладки хранится в `BufferTab.scroll_y`, свапается при переключении (после закрытия вкладки индекс-владелец может на один кадр указать на соседку — визуально самокорректируется).

**D8.5 Статус-бар (3.5).** Слева: транзиентное сообщение ИЛИ `кодировка | переводы строк | Ln L, Col C | язык` — `doc.encoding().label()`, `doc.line_endings().dominant().label()`, позиция каретки (1-based), `language.rs`; справа — «notepad+». Обновление — на каждый `cx.notify()` (движение каретки/переключение вкладки). Язык: минимальный статический маппинг расширение → имя (~40 записей, регистронезависимо; rs→Rust, py→Python, md→Markdown…), untitled/без расширения/неизвестное → «Plain Text»; полное определение (эвристика по содержимому, ручной выбор) — задача 5.1.

Строки UI — английские захардкоженные (i18n — 8.4).

### D9. Editor-виджет — группа 4 (окт 2026)

Нумерация по договорённости: по одному подразделу на задачу 4.1–4.6 (D3–D8 заняты).

**D9.1 Рендер (4.1).** Каретка/выделения рендерятся «разрезом строки» (обобщение D8.1): `split_line` режет текст в char-границах кареток и концов выделений, между кусками — 2px-див каретки, куски внутри выделений получают фоновую подложку (0x264f78); позиции точные без метрик шрифта, табы не ломает. Подложка выделения обязана висеть на div-e СВОЕГО сегмента, а не контейнера строки — иначе любое частичное выделение красит строку целиком (баг пойман ручной проверкой 4.3: модель держала частичный диапазон, рендер заливал строки; регрессионный GUI-тест `selection_background_hugs_segment_not_line` проверяет ШИРИНЫ отрисованных сегментов через `debug_selector`/`debug_bounds` — юнит-тесты `split_line`/`line_carets` этого класса ошибок не видят, они проверяют данные, а не построение div-ов). Источник кареток — `line_carets(&[Selection], doc, line)`: пересечение каждого курсора со строкой (терминатор не подсвечивается). Подсветка активной строки — по ГЛАВНОЙ каретке (последний курсор) и только когда она — чистая каретка без выделения. Бенчмарк 20 МБ: инструментирование в процессоре uniform_list (паттерн spike) — кадры дороже 8 мс печатаются в stderr; файл 20.3 МБ (`/tmp/notepad-bench-20mb.txt`, 290k строк) генерируется скриптом, открывается через `NOTEPAD_OPEN=<path>` (env-override в main.rs, добавлен для бенчмарка — без диалогов); smoke-запуск — ни одного кадра выше порога; интерактивная прокрутка — вручную. Для разбора «живых» проблем мыши добавлена диагностика `NOTEPAD_DEBUG_MOUSE=1`: каждое событие логируется в stderr с сырыми координатами, bounds, advance и вычисленной (line, col). Замечено и исправлено попутно: `UniformListScrollHandle` никогда не был привязан к uniform_list (`.track_scroll` отсутствовал со времён группы 3) — восстановление scroll-позиции вкладок работало вхолостую.

**D9.2 Навигация (4.2).** Страница PgUp/PgDn = вся видимая высота uniform_list в строках: `editor_bounds().height / LINE_HEIGHT` (bounds из scroll-хендла после первой отрисовки; до неё — viewport − 32 таб-бар − 24 статус-бар), минимум 1. Клик: (строка, колонка) из window-координат мыши — `visible_line_at_y`: `floor((y − bounds.top − offset.y) / LINE_HEIGHT)` (offset.y отрицателен при прокрутке вниз — сверено тестом `click_positions_caret`), колонка = `round((x − bounds.left − GUTTER_W) / char_advance)`, clamp по длине строки делает модель. `char_advance` измеряется ОДИН раз: `window.text_system().ch_advance(resolve_font(Menlo), 13px)` — advance «0» моноширинного Menlo (`WindowTextSystem` deref'ится к `TextSystem`); fallback 0.6em, если текстовая система недоступна. Ограничение MVP: таб-стопы в расчёт колонки не входят (документ с табами кликается с погрешностью). Мышь: якорь на mouse_down, живой drag на mouse_move по строкам, commit на mouse_up (контейнер редактора ловит up независимо от строки — click не срабатывает при межстрочном драге, поэтому up слушает контейнер). Shift+клик — расширение от якоря. Цель по столбцу (`goal_col`): заводится на первое вертикальное движение, держится до горизонтального/клика/ввода; при мульти-курсоре не хранится (кламп по столбцу каждой строки). Cmd+G — overlay-диалог ВНУТРИ окна (без нового окна): ребёнок КОРНЕВНОГО div (не поддерева редактора) — фокус в диалоге, клавиши не доходят до `handle_key`; ввод цифр/backspace, Enter → прыжок (`set_caret_at` + `scroll_to_item(Center)` через мапу видимых), Escape — отмена. Клавиатурные имена: `pageup`/`pagedown`/`f2`/`escape` (mac-маппинг gpui).

**D9.3 Мульти-курсор (4.3).** `BufferTab.cursor: Selection` → `cursors: Vec<Selection>`; ГЛАВНЫЙ — ПОСЛЕДНИЙ элемент (Cmd+клик/Cmd+D аппендят — новый курсор сразу главный; статус-бар и активная строка — по нему). Единая политика после ЛЮБОГО редактирования: курсоры схлопываются в каретки в головах (map_selection оставляет выделение поверх вставки — D2.2 делегирует это виджету), дубликаты удаляются с сохранением ПОЗДНЕГО вхождения (пересекающиеся правки Transaction отбрасывает — курсоры могли сойтись). Движение без shift двигает ВСЕ курсоры; shift+стрелки расширяют ТОЛЬКО главный (якоря прочих неподвижны); undo/redo клампит головы в границы документа. Cmd+клик — каретка в точке; повторный Cmd+клик в ту же точку снимает курсор (toggle, как в VS Code; последний курсор не снимается). Alt/Cmd+drag — column selection: прямоугольник якорь→голова, по каретке/выделению `[min_col..max_col)` на каждую строку, кламп по длине (строка короче min_col → каретка в её конце, VS Code-семантика); живой предпросмотр на mouse_move, commit уже стоит на mouse_up. Cmd+D (`add_next_word_match`): первый вызов выделяет слово под главным курсором (границы: буква/цифра/`_`; каретка сразу после слова — слово слева), следующий — добавляет следующее вхождение ТОГО ЖЕ ТЕКСТА после конца главного выделения, затем циклически с начала, без пересечений с существующими курсорами; исчерпание — no-op. Ввод/удаление — штатные свободные функции editor-core над `&[Selection]`. Drag-предпросмотр обычного выделения — `select_to` на каждый move (изменение позиции проверяется — лишних notify нет). Жесты мыши (не горячие клавиши, добавлены по итогам ручной проверки: выделить слово мышью было нечем): **двойной клик — слово** (`select_word_at`), **тройной — строка с терминатором** (`select_line_at`); на этих кликах drag-состояние не заводится. Подсветка текущей строки (серый CARET_LINE) не равна выделению (синий SELECTION) — при непустом главном выделении подсветка строки скрыта (D9.1), что делает выделение слова визуально очевидным. Тестируемость клавиш: в gpui-тестах `main()` не выполняется и keymap приложения пуст — все биндинги через `simulate_keystrokes` не доходят; E2E-тесты клавиш (`cmd_d_keybinding_path`, `cmd_g_keybinding_path`) регистрируют те же биндинги через `TestAppContext::update(bind_app_keys)` перед созданием окна (keymap общий, виден созданным позже окнам).

**D9.4 Закладки (4.4).** Toggle — Cmd+F2 на строке ГЛАВНОЙ каретки; F2/Shift+F2 — следующая/предыдущая ПО КРУГУ от строки главного курсора (`LineMeta::next/prev_bookmark` уже циклические), каретка (единственная, `set_caret_at`) в начало строки закладки + `scroll_to_item(Center)`. Маркер гуттера: строка-ряд = [зона закладки 14px «●» (клик — toggle, stop_propagation чтобы не двигать каретку) | номер строки | зона фолда 14px]; номера — real-строки даже при свёрнутых телах. Панель закладок — секция «BOOKMARKS (N)» внизу ЛЕВОЙ панели «EXPLORER» (решение: боковая панель постоянная, не отдельное окно): записи «номер + содержимое строки», клик — переход. Undo/redo: флаги в LineMeta синхронизируются в `Document::apply` (D2.3) — покрыто отдельным тестом и на модели, и GUI-путём (вставка строк выше сдвигает закладку за содержимым).

**D9.5 Свёртывание (4.5).** Блоки — по отступам (indent-based MVP): заголовок + непрерывный диапазон строк с большим отступом; пустые строки принадлежат телу, если за ними в блоке есть непустые (хвостовые пустые тело не продлевают); таб = 4 пробела; синтаксисные диапазоны (5.1) заменят `fold_end`, интерфейс не меняется. Folded-флаг — в `LineMeta` ЗАГОЛОВКА (переживает undo/redo). uniform_list индексирует строки напрямую, поэтому выбрана МАПА ВИДИМЫХ строк: `folding::visible_lines(doc) -> Vec<usize>` (visible→real), кэш в Workspace `(индекс вкладки, view_version, map)`; `BufferTab.view_version` растёт при правках/undo/redo/фолдах (закладки — нет: мапу не меняют), пересчёт O(n) на изменение. Обратный переход — бинарный поиск. Координаты через мапу: клики (visible_line_at_y → visible_to_real), скролл (real_to_visible), Cmd+G на скрытую строку → каретка на заголовок фолда. Вертикальное движение тел не заходит: вниз — `first_visible_at_or_after` (перепрыгивает тело), вверх — `visible_line_or_header` (к заголовку). Маркеры гуттера: ▾ (есть тело) / ▸ (свёрнут), клик — toggle. «Свернуть всё/развернуть всё» — пункты меню View (горячих клавиш нет — 8.5).

**D9.6 Операции со строками (4.6).** Размещение — editor-core, модуль `line_ops.rs` (решение зафиксировано): чистые функции `Document → Transaction` (сортировка asc/desc × регистр, дедупликация первых вхождений, удаление пустых, регистры), тесты без GUI; приложение только вычисляет scope и применяет через `History` (undo работает автоматически). Scope: строки, пересекаемые НЕпустыми выделениями (объединение по всем курсорам; конец выделения в колонке 0 строку не захватывает); нет непустых выделений → весь файл, исключая фантомную хвостовую пустую строку ropey. Терминатор блока определяется по символу перед концом диапазона (иначе потеря `\n` на хвостовом переводе). Регистры: применяются к ДИАПАЗОНАМ выделений (не к строкам), нет выделений — весь файл; 1:1 по символам для ASCII, многозначные отображения (ß→SS) могут изменить длину — компромисс принят (спека требует неизменность длины на ASCII-сценарии). После строковых операций курсоры схлопываются в каретки (общая политика apply_tx). Scope/применение — в tab_model (GPUI-free, тесты есть); точки запуска — меню «Text» (10 пунктов, без горячих клавиш — раскладка в 8.5).

### D11. Производительность (проход по оптимизациям, окт 2026)

Цель из требований: мгновенное открытие файлов до 200 МБ и отзывчивость
на них. Архитектура, API и поведение не менялись — только скорость и
память. Все 171 тест остались зелёными (+5 новых, см. D11.6).

**D11.1 Стенд и методология.**

- Генератор файлов `scripts/bench/gen_files.sh` → `/tmp/notepad-bench`:
  профили × размеры — short (короткие строки ~70 Б с multibyte «—», 1/20/100/200 МБ),
  cyr (UTF-8 кириллица, 1/20/100/200 МБ), long (~1 КБ строки), empty
  (каждая третья пустая), code (вложенные отступы) — 20/200 МБ;
  кодировочные варианты: UTF-8+BOM, UTF-16LE+BOM, windows-1251 (iconv).
- Env-режим `NOTEPAD_BENCH=1` (модуль `crates/app/src/bench.rs`,
  env-гейтирован, в продукте выключен): при старте открывает
  `NOTEPAD_OPEN`, печатает в stderr тайминги — открытие
  (BufferTab::open), первый кадр после открытия, холодный старт
  main→первый кадр, скролл N прыжков по псевдослучайным строкам
  (детерминированный LCG), тайпинг M символов через модель
  (GPUI-free путь `BufferTab::insert_text`), undo/redo всей группы.

Оптимизации (поведение побайтово то же):
1. **Отложенное кормление chardetng** (encoding.rs): детектор не кормится
   в проходе UTF-8-валидации; при первом malformed-байте файл
   перечитывается и детектор получает те же байты — до конца куска с
   malformed включительно, как при кормлении на лету (статистика
   chardetng зависит от потока байт, не от разбиения) → `guess`
   детерминированно тот же. Для валидных UTF-8 файлов (99.9%)
   детекция вообще не выполняется — её результат неиспользуем.
   Худший случай (malformed в конце файла): +1 перечитывание валидной
   части — сознательный компромисс.
2. **Fast-path нормализатора переводов строк**: кусок без `\r` —
   `push_str` целиком + счёт LF по байтам (автовекторизация) вместо
   посимвольного автомата (297→115 мс на 200 МБ). pending-CR через
   границу кусков и куски с `\r` — прежний посимвольный путь.
3. **LineMeta::with_lines — O(n)-построение** вместо n одиночных
   `merge` (572→73 мс на 9.4М строк; 164→18 мс на 2.9М):
   сбалансированное по midpoint дерево за один проход, приоритеты —
   старшие 8 бит монотонны по глубине (max-heap по построению),
   младшие 56 бит из того же splitmix64-потока (детерминизм);
   `reserve_exact(count)` убивает транзиентную память реаллокаций арены.

### D12. Подсветка синтаксиса — группа 5 (окт 2026)

Спека specs/syntax-highlighting: автоопределение языка (расширение →
содержимое) + ручной выбор, инкрементальная раскраска видимых строк
через syntect с кэшем на строку, порог отключения 20 МБ, покрытие 70+
языков. Аддитивный слой: движок — GPUI-free в editor-core
(`syntax.rs` — детект, `highlight.rs` — раскраска), app — кэш/рендер
(движок живёт в `BufferTab`, классы → палитра theme.rs, оверлей выбора
языка `language_dialog.rs` по паттерну goto_dialog).

**D12.1 Архитектура, кэш, инвалидация.**

- **Язык файла**: `TabLanguage` в `BufferTab` — авто-детект
  `(грамматика, метка)` + ручной override (Auto/PlainText/Syntax) +
  флаг порога. Детект `editor_core::syntax::detect_labeled`:
  расширение → (без расширения) первая строка ~1 КБ
  (`find_syntax_by_first_line`: shebang, `<?php`, …). Метка ≠ имя
  грамматики для псевдонимов (TypeScript → JS-грамматика, метка
  «TypeScript»); friendly-имена для статус-бара («Bourne Again Shell
  (bash)» → «Shell»). Набор `load_defaults_newlines()` — глобальный
  `OnceLock`; открытие файла детектит ТОЛЬКО если набор уже прогрет
  (`try_syntax_set`), иначе язык до прогрева — «Plain Text».
  **Прогрев** — отложенная задача из первого `render` (спавн + 50 мс):
  инициализация набора (~96 мс release), детект всех вкладок,
  `ensure_window(0..64)` активной — разовая ленивая десериализация
  контекстов (`SyntaxReference.lazy_contexts`, OnceCell — ~1–3 мс на
  синтаксис) и компиляция regex'ов (onig OnceCell, ~1.4 мс первая
  строка) уходят с рендер-пути. Холодный старт и открытие syntect не
  платят (замеры D12.2).
- **parse-state (ключевой дизайн-вопрос; выбор по замерам
  `bench_highlight_components`)** — ГИБРИД вариантов (а)+(б):
  1. **Чекпоинты** `(ParseState, ScopeStack)` каждые 1024 строки
     разобранной области — прыжки назад/внутри разобранного почти
     бесплатны. Обе половины обязательны: `ParseState` — контексты
     грамматики, `ScopeStack` — скоупы цвета (HighlightLines держит
     обе; сохранять только ParseState нельзя).
  2. **Стеки на каждую строку окна** (~35–60 записей, чистятся при
     сдвиге окна): правка инвалидирует от строки правки, ближайший
     валидный стек — в пределах окна → переразбор правки ≈ окно
     (~1.5–2.5 мс), а не 1024 строки.
  3. **Догон с бюджетом времени**: прыжок в неразобранную область
     продвигает разбор от ближайшего чекпоинта порциями ≤2 мс на кадр
     (`CATCH_UP_BUDGET`), прогресс сохраняется между кадрами; окно
     подсвечивается прогрессивно, фризов нет. Скорость разбора
     стенда ~23–24 тыс. строк/с (43 µs/строку, профиль code) —
     прыжок к концу 20 МБ файла догоняется за ~6–7 с прогрессивно,
     кадры при этом ≤2.6 мс.
  Альтернатива (в) stateless-per-line отвергнут: ломает
  многострочные конструкции (docstring/блочные строки — тест
  `multiline_state_carries_over`).
- **Кэш спанов**: `HashMap<строка, Arc<Vec<Span>>>` в
  `HighlightEngine` (владелец `BufferTab` — вне процессора
  uniform_list, не переаллоцируется на кадр); спаны — char-диапазоны
  строки без терминатора + класс (7 классов: comment/string/keyword/
  number/function/type/constant). Потолок 16384 записей, чистка вне
  окна ±4096. Догон и окно собирают спаны одинаково — иначе зона
  догонa перепарсивалась каждым кадром (ловушка, поймана бенчмарком:
  тёплый кадр деградировал до 2 мс; после фикса — 6 мкс).
- **Инвалидация**: правка — `invalidate_from(первая строка правки в
  до-координатах)`: спаны `≥ line` и стеки `> line` сбрасываются,
  строки выше правки и кэш survives; undo/redo — полный сброс (строки
  правок внутри History неизвестны); каретки/выделения кэш не трогают
  (тест). Дедлайн догонa ставится ПОСЛЕ инициализации состояния —
  разовая ленивая цена синтаксиса не ест бюджет кадра (ловушка,
  поймана на debug-сборке).
- **Вложение цвета в рендер**: `split_line_styled(content, carets,
  sel_ranges, colors)` — обобщение `split_line` (D9.1): границы
  кареток/выделений + границы цветов; цвет вешается на div сегмента,
  фон выделения остаётся на своём сегменте; класс 0/None цвет не
  задаёт — наследуется TEXT. Round-trip: пустые `colors` → вывод
  бит-в-бит как `split_line` (юнит-тесты 4.1 + GUI-тест
  `plain_file_single_segment_round_trip`). Проверено пробником:
  пробельные текст-узлы в gpui 0.2.2 НЕ схлопываются (ширина
  сохраняется при любом разрезе).
- **Оверлей ручного выбора** (клик по языку в статус-баре):
  список «Auto-detect» / «Plain Text» / ~64 языка с фильтрацией
  вводом; Enter — первый видимый, Escape — отмена. Дочерний div
  КОРНЯ, фокус отдельный handle (ловушка D9.2). Смена языка
  применяет грамматику немедленно (кэш движка сбрасывается при смене
  имени синтаксиса). После save-as пере-детект по новому расширению.

- **D9.5 fold-обещание «синтаксисные диапазоны заменят fold_end» —

**D12.4 CSV-подсветка и порог по согласию пользователя (правка спеки, окт 2026).**

- **CSV/TSV: колонки чередуются цветами.** Sublime-грамматика не умеет
  индексные цвета — цветовые диапазоны строит сам движок:
  `HighlightEngine` распознаёт синтаксис по имени «CSV» (грамматика-
  заглушка с расширениями csv/tsv — для детекта и списка выбора) и
  зовёт `csv_spans` вместо syntect-парсера. Разделитель — большинством
  в строке (`,` для CSV, `\t` для TSV, ничья → запятая; построчно,
  stateless — состояние разбора проходит насквозь); кавычки RFC-4180:
  разделитель и `""` внутри `"…"` не делят поле. Классы
  `CLASS_COLUMN_A..D` (ротация 4 цветов Dark+: голубой/оранжевый/
  зелёный/золотой — соседние колонки всегда различимы); пустые поля
  не красятся, но индекс колонки считают. Кап длины строки действует
  как для остальных. Разделители между полями рендерятся plain-
  сегментами (не красятся).
- **Порог 20 МБ → вопрос пользователю (правка спеки).** Файл больше
  20 МиБ открывается без подсветки (`over_threshold`), приложение
  спрашивает модальным `Window::prompt` «Enable / Keep off»
  (согласие → подсветка файла ЛЮБОГО размера, отказ → сообщение в
  статус-бар, редактирование полноценно). Согласие включает
  `threshold_allowed` + детект языка; движок красит любой размер —
  бюджет догонa (2 мс/кадр) держит кадры и на 200 МБ, полный догон
  просто прогрессивнее (~2,5 мин для 2,9М строк; правки пересчитывают
  только окно — стеки окна инвариантны размеру файла). Повторный шанс
  — клик по языку в статус-баре на вкладке без разрешения спрашивает
  снова. Bench-режим (`NOTEPAD_BENCH=1`) не спрашивает — стенд
  остаётся неинтерактивным (цифры D11/D12.2 без изменений).
  Очередь вопроса: диалог требует Window — сессия/NOTEPAD_OPEN
  собирают вкладки в `pending_threshold_tabs` до создания окна,
  `open_paths` спрашивает сразу. Один диалог на все новые крупные
  файлы открытия (N файлов — суммарный вопрос; per-file цепочки
  диалогов отвергнуты как шум).

**D12.5 Липкая шапка CSV (задача 5.7, окт 2026).**

- **Видимость**: предикат `geometry::sticky_header_visible(offset_y)` —
  `|offset.y| ≥ LINE_HEIGHT` (offset.y отрицателен при прокрутке вниз,
  положительный — овёрскролл-отскок: строка 0 видна, шапки нет).
  Частичный показ (0 < |offset| < LINE_HEIGHT) шапку НЕ дублирует —
  дубль поверх наполовину видимой строки 0 мерцает. Оверлей — дочерний
  ABSOLUTE div контейнера редактора (`render_editor`; контейнер
  `.relative()` — якорь), добавленный ПОСЛЕ uniform_list: top 0, вся
  ширина, высота LINE_HEIGHT, гуттер с номером 1 + текстовая ячейка с
  ЦВЕТАМИ КОЛОНОК (split_line_styled по спанам строки 0, кареток/
  выделений в копии нет), сплошной фон CSV_HEADER_BG + нижняя РАМКА
  border_b_1 CSV_HEADER_BORDER (тема). Спаны строки 0 прогреваются в
  render_editor ДО чтения (`ensure_window(0..1)` — CSV stateless,
  микросекунды; нужен `&mut` вкладки, ниже она только читается).
- **Перерисовка при скролле (спайк, главный риск задачи)**: колесо
  мыши в gpui 0.2.2 идёт через `Interactivity::paint_scroll_listener`
  (elements/div.rs): bubble-фаза + `hitbox.should_handle_scroll`,
  `scroll_offset.y += delta` в общем `Rc<RefCell<Point>>` (ЕГО ЖЕ
  хранит ScrollHandle — `Interactivity::request_layout` клонирует Rc
  из handle, поэтому `base_handle.offset()` и layout читают одно
  значение) и `cx.notify(current_view)` — current_view при покраске
  uniform_list в дереве Workspace = сам Workspace → render
  перезапускается на каждый скролл, оверлей обновляется. Fallback
  (подписка/чтение offset на paint-фазе) НЕ потребовался.
- **Ловушка deferred-скролла (поймана GUI-тестом)**:
  `scroll_to_item` откладывает применение в prepaint ПОСЛЕ render —
  кадр строится по СТАРОМУ offset: оверлей опаздывает на кадр, а после
  клика по шапке зависал бы до следующего события мыши (up/move без
  драга не нотифицируют). Клики по шапке поэтому ставят offset (0, 0)
  НЕМЕДЛЕННО (тот же общий Rc) + `scroll_to_item(0, Top)` + notify;
  deferred подтвердит значение.
- **На месте**: real-строка 0 при is_csv — фон CSV_HEADER_BG (bg
  применяется после CARET_LINE — перекрывает подсветку активной
  строки) + нижний разделитель АБСОЛОТНЫМ 1px-дивом (якорь —
  `.relative()` на строке): border на строке списка ломает разметку
  uniform_list (строка обязана быть ровно LINE_HEIGHT), absolute не
  влияет на layout — высоты/координаты строк не меняются. РАМКУ
  (border_b_1) несёт только оверлей.
- **is_csv** (`BufferTab`): грамматика «CSV» (детект/ручной выбор)
  ИЛИ расширение пути .csv/.tsv (регистронезависимо). Порог-отключение
  подсветки (>20 МБ, отказ) шапку НЕ отключает — липнет без спанов
  (рекомендация задачника принята: ensure_window без синтаксиса —
  no-op, spans(0) → None → копия без цветов). Фолды: шапка рендерит
  REAL-строку 0 напрямую (мапу visible→real не использует — видимый
  индекс 0 при фолдах не тождественен real 0). Хвосты: пустой/
  однострочный CSV скроллится не дальше строки 0 — guard по offset
  покрывает, шапка не рисуется поверх самой себя.
- **Клики**: id + on_mouse_down + stop_propagation (паттерн зон
  гуттера): bubble-фаза gpui диспетчеризует листенеры в ОБРАТНОМ
  порядке регистрации — оверлей, покрашенный после списка, ловит клик
  раньше контейнера редактора. Оверлей перекрывает первую видимую
  строку — нормально для липкой шапки.
- **Бенчмарк csv-19mb.csv (release)**: load 12.2–13.8 мс (было ~13);
  скролл кадр p95 2.30 мс (было 2.2), тайпинг кадр p95 2.27 (было
  2.1) — уровень бюджета догонa подсветки (2 мс), стоимость оверлея в
  кадре не различима (render p95 0.17–0.29 мс, включая шапку).
- **Тесты**: 226 → 230. Юнит: `sticky_header_visibility_predicate`
  (0 / частичный / полный / глубокий / овърскролл),
  `is_csv_for_csv_tsv_and_non_csv` (csv/tsv/C.CSV/txt/untitled/
  ручной выбор; холодный/тёплый набор детекта не меняет результат).
  GUI: `csv_sticky_header_pins_and_click_scrolls_to_top` (закрепление
  при прокрутке, ширина ≈ редактору, высота = LINE_HEIGHT, сегменты =
  строке 0 «name,count,note» → 5, клик → offset 0 + шапка исчезла +
  выделение на месте), `csv_sticky_header_partial_and_plain_files`

### D13. Поиск и замена — группа 6 (окт 2026)

Спека specs/search-replace: поиск/замена в файле (текст/regex/регистр/
целые слова, подсветка всех совпадений, замена по одному/все, группы
захвата `$1`), поиск по открытым вкладкам, поиск по файлам папки
(маска, потоковые результаты) и замена по файлам через изменённые
вкладки. Аддитивный слой по образцу группы 5: движок — GPUI-free в
editor-core (`search.rs`), UI — app (`search_panel.rs`, секция SEARCH в
`project_panel.rs`, подсветка в `editor_view.rs`).

**D13.1 Движок (editor-core/src/search.rs).**

- **Matcher**: `SearchMatcher::new(pattern, SearchOptions {case,
  whole_word, regex})` → всегда fancy-regex (текст — `escape`;
  lookaround — причина выбора по D2). Ловушка fancy-regex 0.14
  (поймана мини-стендом): опция `RegexBuilder::case_insensitive` НЕ
  пробрасывается в делегированный regex crate — регистр отключается
  ИНЛАЙН-флагом `(?i)` префиксом. Целые слова: `\b` только на word-
  краях паттерна (поиск `...` с безусловной `\b` не матчится вовсе);
  граница — по ВСЕМУ паттерну. Ошибка компиляции — `Err(String)` →
  панель + статус-бар, никогда не паника. Совпадения нулевой длины
  (`a*`) не собираются — защита бесконечной итерации; ограничение
  зафиксировано.
- **Чанковый проход (память D11.4)**: rope НЕ материализуется — чанки
  накапливаются в буфер до 256 КБ, regex по буферу, уверенно берутся
  совпадения, начинающиеся до `len − SEARCH_OVERLAP` (1024 Б), затем
  буфер сдвигается (хвост-1024 переносится). Совпадение через границу
  чанков/окон находится в следующем окне (тест на 300 КБ документе
  сверяет с эталоном по цельной строке, совпадение ровно на границе
  256 КБ присутствует). **Остаточное ограничение**: lookbehind длиннее
  1024 Б, начинающийся до начала окна/зоны пересчёта, может дать иное
  совпадение, чем полный поиск одной строкой; совпадения длиннее
  буфера не ищутся. char↔byte — `Rope::byte_to_char` от глобального
  байтового начала буфера (паттерн build_spans). Ловушка (поймана
  падением в живом окне на кириллице, окт 2026): сдвиг окна
  `len − SEARCH_OVERLAP` — чисто байтовая арифметика и может попастьнуть
  ВНУТРЬ multibyte-символа — паника среза; `shift_window` округляет
  границу вниз до ближайшей char-границы, регрессионный тест крутит
  документ 48 смещениями префикса (граница окна гарантированно
  оказывается посреди кириллического символа).
- **Замена**: тот же проход, `captures_iter` + `Captures::expand`
  (`$1`/`$имя`; текстовый режим — литеральная замена, `$1` не
  разворачивается). Правки — `Vec<(start_char, end_char, text)>` в
  до-координатах; app применяет их ОДНОЙ составной транзакцией
  `BufferTab::apply_search_edits` (по образцу insert_text; undo одним
  шагом — составная правка не группируется с вводом, D2.4).
- **Скан папки**: `collect_files` (обход std::fs, симлинки пропускаются
  — циклы, сортировка — детерминизм) + маска-глоб руками
  (`*`, `?`, `{a,b}` одна вложенность; к ИМЕНИ файла,
  регистронезависимо-ASCII — Windows-привычка; пустая = все) +
  `scan_file` (memmap2; NUL в первых 8 КБ → бинарный пропуск; BOM-
  файлы UTF-16 содержат NUL легально — бинарный детект только без
  BOM, ловушка поймана тестом) + `scan_paths` (rayon `par_chunks(16)`,
  батчи через колбэк из rayon-потоков). **Кодировки** (компромисс и
  границы): UTF-8 валид → как есть; BOM → фиксированное декодирование;
  иначе chardetng по префиксу 64 КБ и lossy-декод всего файла — поиск
  по декодированной строке; для экзотических коротких файлов детектор
  может ошибиться (граница компромисса), insertion lossy U+FFFD.
- **Замеры (release, /tmp/notepad-bench-подобный контент 20 МБ)**:
  текст-поиск полный ≈ 3.7 мс (по чанкам; цельной строкой 3.3),
  regex ≈ 4.7 мс, хвостовой пересчёт от середины ≈ 1.5 мс; 100 файлов
  (~2.6 МБ) scan_paths ≈ 0.02 с (бюджет 2 с, тест
  `scan_hundred_files_under_two_seconds`, debug-порог 20 с).

**D13.2 Панель (6.1/6.2) — app/search_panel.rs.** Постоянная пока
открыта (Cmd+F; НЕ модальное окно, паттерн VS Code), абсолютный

- **Лупа-кнопка 🔍** рядом с полем запроса (замечание юзабилити):

- **Подсветка в рендере**: `split_line_full` (обобщение
  split_line_styled) режет строку ещё и по границам совпадений;

   отдельные от SELECTION. Совпадения строки для процессора uniform_list считаются
   ДО мутабельного заёма вкладки (заём-ловушка borrow-чекера).
- **Инвалидация при правках**: `BufferTab.last_edit_line` (apply_tx
  ставит первую строку правки) + `view_version`. Рендер панели

  `find_in_doc_from(line_to_char(line))` с отступом 1024 Б назад

**D13.3 Поиск по вкладкам (6.3).** Cmd+Shift+F — та же панель со
scope Tabs; Enter/лупа — запуск (не живой: объём вкладок не
ограничен). Untitled-вкладки участвуют (контент в памяти, подпись
«Untitled N»). Баг ручной проверки (зависания UI + «куча вхождений» +
повторяющиеся фризы каждые 1–2 с): поиск был СИНХРОННЫМ на UI-потоке,
а результаты не ограничивались — короткий запрос по большой вкладке
давал сотни тысяч `SearchHit` (аллокация фрагмента на каждый), и
не-virtualized секция SEARCH строила div на КАЖДУЮ запись при каждом
рендере. Исправление: поиск ФОНОВЫЙ (ropes клонируются — дерево ropey
дёшево — и ищутся на background executor; `SearchMatcher::
find_in_rope` публичный), результаты КАПЯТСЯ — MAX_HITS_PER_TAB=500 /
MAX_HITS_TOTAL=2000 с пометкой «(truncated)» в сводке; рендер секции
показывает не больше SEARCH_SECTION_MAX_ROWS=300 записей + «…and N
more». Реэкспорт `editor_core::ropey` — app не получает новой
зависимости.
Результаты — `SearchHit { owner: Tab{index,label}, line, col, len,
fragment, frag_col }` — секция **SEARCH** левой панели по образцу
BOOKMARKS (рекомендация задачника принята): заголовок группы при
смене владельца, запись «Ln N + фрагмент», совпадение в фрагменте
подсвечено фоном SEARCH_MATCH; клик — `TabModel::activate` + выделение
совпадения + `scroll_to_line`. Индексы вкладок валидируются при

**D13.4 Поиск по файлам (6.4).** Scope Folder: папка — чип Folder в

truncated, «…and N more» в секции). Вкладки, чьи пути лежат в
папке, ищутся по ИХ содержимому (спека: повторный поиск видит
изменённые вкладки, не диск) — синхронно; остальные файлы — фоновый

статус-бара «N match(es) in M file(s)».

**D13.5 Замена по файлам (6.5).** Кнопка «Replace All…» (scope

ПЕРЕСЧИТЫВАЮТСЯ по вкладке (не по диску) и применяются

актуальное состояние вкладок).

### D14. Воркспейс и дерево проекта — группа 7 (окт 2026)

Структура: `crates/app/src/{fs_tree.rs, fs_watch.rs, tree_panel.rs}`; правки —
workspace.rs (поля дерева/диалогов/watcher, сессия), project_panel.rs (секция
дерева вместо заглушки), tab_model.rs (`retag_path`), actions.rs/main.rs
(действия+биндинги+меню+восстановление). Все 150 тестов app (+11 модели
дерева, 3 watcher, 1 retag, 7 GUI) зелёные.

**D14.1 Модель дерева (7.1).** `FsTree` — GPUI-free: корень + `expanded`/
`selected` (ключи — пути) + кэш детей `HashMap<PathBuf, Rc<Vec<Entry>>>`.
Ленивое чтение: `read_dir` только для папок на пути обхода (`visible_rows`
строит плоский DFS только по раскрытым; корень всегда «раскрыт» — верхний
уровень виден сразу). Сортировка: папки выше файлов, внутри групп
регистронезависимо по имени. Скрытые «.»-записи не показываются (дефолт MVP
без настроек видимости — .DS_Store/.git не шумят); симлинки не
разворачиваются (`DirEntry::file_type` без follow). Ошибка `read_dir` = пустой
список (папка исчезла между событиями — рендер не падает).

**D14.2 Операции и UI (7.2).** Операции FsTree: `create_file/create_dir/
rename/delete/move_into` — fs-вызов + точечный сброс кэша затронутых
каталогов; гварды: имя без `/` и не «.»/«..», не поверх существующего,
перемещение только внутри воркспейса, не в себя/потомка. rename/move
переводят expanded/selected за узлом (`follow_path`) — состояние поддерева не
теряется. UI: строки в панели EXPLORER (отступ по глубине, ▸/▾ у папок);
клик по файлу — вкладка (`open_paths`), по папке — toggle; правый клик —
контекстное меню (New File…/New Folder…/Rename…/Delete; для корня только
создание) — overlay поверх подложки, закрывающей меню кликом мимо
(mouse_down пунктов делает stop_propagation — иначе закрытие съедает click).
Ввод имён — overlay-диалог (паттерн goto D9.2: ребёнок корня, отдельный
фокус; имя заменяется ЦЕЛИКОМ, расширение не сохраняется). Удаление —
модальный `Window::prompt` (Delete/Cancel). Горячие клавиши (действуют по
выделению дерева; нет выделения — создание в корень): Cmd+N файл,
Cmd+Shift+N папка, Shift+F6 rename (F2 занят закладками, IntelliJ-жест),
Cmd+Backspace delete (Finder-стиль; plain delete не вешаем — конфликтовал бы
с вводом в редакторе). **Drag-and-drop**: gpui 0.2.2 `on_drag` требует
ghost-`Entity<W: Render>` (ловушка D8.2) — конструктор создаёт `DragGhost`
(имя узла) через `cx.new`; drop-цели — строки папок и заголовок воркспейса
(`on_drop::<PathBuf>`), подсветка — `on_drag_move` (drop_target), дроп мимо
целей чистит подсветку (on_drop на корне). **Открытые вкладки следуют за
файлом**: `TabModel::retag_path(old, new)` после rename/move (в т.ч.
последующие сохранения идут в новый путь — тест покрывает); удалённый файл —
вкладка остаётся (стандартное поведение редакторов, осознанный MVP).

**D14.3 Watch FS (7.3, D4).** `fs_watch.rs`: `notify::recommended_watcher`
(FSEvents/ReadDirectoryChangesW/inotify), рекурсивно на корень; события
пересылаются в отдельный поток дебаунса: пути копятся, окно 250 мс
переоткладывается каждым событием, по тишине — один батч через
`std::sync::mpsc`. Доставка в gpui — поллинг `try_recv` таймером 150 мс в
`cx.spawn`-задаче (std-канал не Future; smol-канал из gpui 0.2.2 не
реэкспортируется — новая зависимость не введена; ≤150 мс к дебаунсу —
приемлемо для синхронизации дерева). Батч → `FsTree::apply_external`:
полный сброс кэша (D4 fallback — correctness first, повторное чтение лениво)
+ чистка expanded/selected от исчезнувших путей. Смена воркспейса —
`watch_generation`: поллинг старого поколения самоостанавливается. Тест с
tmpdir: реальный watcher (интеграция, таймауты 10 с) — создания коалесятся в
один батч, удаление приносит путь; сравнение путей через `canonicalize`
(macOS FSEvents отдаёт /private/… для /tmp). Внешние переименования НЕ
маппятся на вкладки (notify не даёт надёжного old→new) — вкладки живут со
старым путём, дерево перечитывается; расширение — будущая задача.

**D14.4 Запоминание (7.4).** `SessionState.workspace` (поле существовало со
времени D8.4) наполняется в `session_state()` из корня дерева;
восстановление — main.rs: при старте `state.workspace.filter(is_dir)` →
`open_workspace_folder` (дерево+watcher), исчезнувшая папка тихо
пропускается (дерево открывается заново через Cmd+Shift+O). GUI-тест
фиксирует попадание воркспейса в состояние сессии; bench-режим сессию не
восстанавливает — путь остаётся None.

**Правка по ручной проверке группы 7 (окт 2026):** файловые операции,
undo/redo и навигация жили одним списком в app-меню — привычного меню
«File» не было. Меню разнесены по стандартной структуре macOS: notepad+
(Quit) | File (New File/Folder, Open…, Open Workspace…, Save/Save As…,
Close Tab) | Edit (Undo/Redo) | Navigate (Go to Line…, закладки) | View |
Search | Text.

## Risks / Trade-offs



- [GPUI API нестабилен, churn вместе с Zed] → Pin версии; 1–2-недельный spike в начале: окно + вкладки + rope-редактор с вводом текста; критерий прохождения — spike-приложение открывает файл 5 МБ и редактирует без лагов. Fallback — egui.
- [Свой движок редактора = самая дорогая часть проекта] → Это цена требования «максимальная скорость + нативность». Ограничиваем MVP-скоуп движка ядрами specs (multi-cursor, folding), не гонимся за vim-режимами.
- [syntect медленнее tree-sitter на инкрементальной раскраске] → Раскрашиваем только видимые строки, кэш подсветки на строку; tree-sitter как последующая оптимизация.
- [Нет screen-reader a11y в GPUI] → Принято: персональный инструмент; вне MVP-требований.
- [Порог подсветки зафиксирован: 20 МБ] → Выше порога подсветка отключается автоматически с уведомлением (см. specs/syntax-highlighting).
- [Замена в файлах применяет изменения во вкладки, не на диск] → Зафиксировано по specs/search-replace: заменённые файлы открываются как изменённые вкладки, сохранение за пользователем.

## Migration Plan

Не применимо (greenfield). Порядок: spike → каркас окна/вкладок → текстовая модель → editor-виджет → фичи по specs.
